# android

iikb on Android: the same keyboard, KeyboardCore built for Android with the Swift SDK for Android, under a Kotlin input method that draws and touches as iOS's KeyboardUI does. A sideloaded APK, signed with one release key so each build installs over the last.

- `Package.swift`, `Sources/KeyboardAndroid`: the bridge, a dynamic library `libiikb.so` on KeyboardCore alone (no Foundation but FoundationEssentials, for JSON). `Keyboard` forwards to `TypingEngine` as `FullKeyboardViewController` does; `Bridge.swift` holds the JNI functions Kotlin's `Native` declares; `HostDocument` is the app's field as a `TextDocument`, calling back into Kotlin's `Field` and turning the engine's counts in characters into Android's UTF-16. `Frame` is what Kotlin draws, as JSON. `Clips` holds the clipboard's `ClipboardHistory`, `Gifs` the GIF panel's `GifSearch` and `GifRecents`, `Swatch` a theme's A and B keycaps, `Line` an open chat's `LineDocument`, which `Keyboard.typing` puts in the app's field's place, and `Sources` the sources' `SourceFeed`s.
- `Sources/CJNI`: `jni.h` from the NDK as a module.
- `app/`: the Android app (Kotlin, Compose for the app's pages, a plain `View` for the keys).
  - `keyboard/IikbService`: the input method. One event is one batch edit on the field, then a new `Frame`. Suggestions rank on a background thread (`suggestionJob`), as on iOS.
  - `keyboard/KeyboardView`: the bar and keys from the `Frame`, and touches read as `KeyboardView+Touches.swift` reads them; `KeyPainter` paints a key as `KeyView` does; `Glyphs` draws SF Symbols' names with paths of its own (SF Symbols and SF fonts are Apple's alone).
  - `keyboard/Overlay`: the menu and the panels opened from it (`Menu`, `ClipboardPanel`, `TranscriptsPanel`, `GifPanel`, `LookRows`), drawn with Compose over `KeyboardView`, in the keys' place or, with the keys up, in the bar's. `EmojiPanel` stays on the keys' canvas. A held clip, transcript or GIF shows on `Overlay.peek`, a layer over the whole keyboard (`Peek`), as iOS's context menu does: all of it on a card, the keyboard dimmed behind it, its actions in a menu under it.
  - `keyboard/Clips`: the clipboard's history, one per process, so the keyboard and the app's Clipboard tab share it. The keyboard keeps a clip by the time Android says it was copied, never one an app marks sensitive or one copied in a password or incognito field. A copied image is kept as a file under its SHA-256, as on iOS; picked in the keyboard, it goes into the field through `commitContent` where the app says the field takes that type, and onto the clipboard elsewhere.
  - `keyboard/Klipy`, `keyboard/Gifs`: KLIPY's GIFs, its key copied into the assets from `Resources/Keys/klipy.key` at build time (out of git); a tapped GIF goes on the clipboard through the app's `FileProvider`, never into the history.
  - `Services`: the extensions and sources you added, kept in the settings prefs under iOS's names; `iikb://extension` and `iikb://source` links add one from `MainActivity`, after asking.
  - `keyboard/Sources`: what each source is told (docs/sources.md), as iOS's `Sources`: KeyboardCore's `SourceFeed` picks each update, posted off the main thread, and the hint shows in the suggestions' place until tapped. A field's id is new each time the keyboard starts in it, as iOS's `documentIdentifier`; password fields and those asking for no learning (an incognito tab) are never sent.
  - The personal dictionary: Android's `UserDictionary`, which only the keyboard in use may read, stands in for iOS's supplementary lexicon (`Native.learnLexicon`): a word's shortcut is a Text Replacement, a word without one is kept as yours. Settings › Typing opens Android's page for it.
  - `keyboard/Chats`, `keyboard/ChatPanel`: the extensions' chats: listed while the menu is out, the open one asked for again as each answer comes. While a chat is open the keys type into its line, return sends it, and the chats sit as pills in the bar (`KeyboardView.chats`). A message is real text: held, it selects with the system's handles and text toolbar; its links and web addresses open in the phone's app for links (`openLink`), and a link held offers Open Link and Copy Link on `Overlay.peek`. `iikb://extension` links add one from `MainActivity`; `res/xml/network.xml` allows http only on `localhost` and `.local`, as iOS does.
  - Backup: Android's own Auto Backup, to the phone's Google account, takes the files and settings (`allowBackup`), all but `noBackupFilesDir` (recordings, the voice model) and the cache. iOS's backup server (docs/backup.md) is a personal build's, so the APK, which goes to other people, has none.
  - `keyboard/Field`: Android's `InputConnection` as the engine reads and edits it. A return the app takes as its action (send, search, go) goes to it as that action.
  - `voice/`: voice typing, in the keyboard itself, since Android lets a keyboard use the microphone (see "Voice typing").
  - `keyboard/MicBar`: the bar's mic, as docs/design.md's "The mic" and KeyboardUI's `SuggestionBar` and `MicButton` draw it: the recording capsule (`Waveform`) with its cancel, the stop animation Settings › Appearance picks (Squeeze, Drain or Card), a cancelled recording turned to dust (`Dust`), the waiting dictations' cards (`PendingStack`), the Record Key in the bottom row when it's on, and iOS's green dot on both while a tap records in place (`ready`: Home's switch on and the microphone allowed). Its motion runs on `Motion`'s springs and UIKit curves, on a clock that follows Android's animator duration scale, so Developer options › Animator duration scale slows it to watch frame by frame.
  - `Folds`: whether the phone folds (it has a hinge). One that does stays a phone open or folded, as iOS's iPhone Duo does (`DeviceClass(screen:folds:)`), so open (600 dp or more on the short side, the screen's size and never the hinge deciding) it lays out the open Duo's keys and splits them in landscape when Split Keyboard is on, which Appearance lists only on a phone that folds. Anything else that wide is a tablet, as an iPad is.
  - `Transcripts`: every dictation, one store the keyboard and the app share (see "Voice typing").
  - `Settings`: the settings, under the names iOS's `SettingsStore` keeps them.
  - `Vocabulary`: your Dictionary, iOS's `vocabulary.json`, which `corrected` puts on a dictation.
  - `app/stats/Computers`: the computers Stats shows beside the phone (docs/computers.md), each read from its address as Stats comes forward, the list in the files Auto Backup keeps and each one's last answer in the cache. An `iikb://computer` link adds one from `MainActivity` and opens Stats on it, as iOS's does, without asking, since it only reads.
  - `app/Glass`: iOS 26's glass, drawn by Kyant's backdrop library: the tab bar blurs and bends the page scrolling under it (Android 12 and 13 on, the tint alone before); Back, the mic switch and Stats' device button sit over a plain page, so they take its rim, tint and shadow.
  - `app/`: the app's pages, in iOS's look (`Style`, `Rows`, `Symbols` for its SF Symbols): `Home`, the Settings list and its pages (`SettingsPages`, `KeyboardPages`, `WritingStyle` with Style in Each App, `Dictionary`, `ServicesPage` for Extensions and Sources). `App`'s `TabBar` is the iPhone's tab bar, a floating capsule of filled glyphs over their names. `Core` asks the engine what they show (`Sources/KeyboardAndroid/App.swift`): the Keyboard pages' preview, a `KeyboardView` on a keyboard of its own over an empty `PreviewField`; Writing Style's examples; which layout settings apply on this screen; taps learned. Settings › Changelog reads `changelog.json`, which the build writes from `Changelog:` trailers as scripts/phone does for iOS. Someone on Android has never seen iOS's app, so a trailer here never compares with it ("as on iOS"); `changelog.tsv` rewords a line already in history, by its commit.
- The English data (`KeyboardEnglish/Resources`) goes into the APK's assets uncompressed, and the engine reads it mapped, in place.

## Voice typing

As on iOS (App/Voice/AGENTS.md), recording and writing never wait on each other: `Microphone` records 16 kHz mono with Android's speech-recognition source and knows nothing of the models, and once you stop, `Dictation` hands the finished `Recording` to the model, one at a time in the order said, while the next records. What the model heard is styled in Settings › Writing Style for the app it was said for (`Native.written`), then run through your Dictionary (`Vocabulary.corrected`, with the English lexicon, so a made-up word that sounds like a term becomes it), together the iOS app's `DictationWriting.typed`, and typed through the engine as `KeyboardEvent.dictated`, but only into the field it was said in (`fieldCount`); said elsewhere, it's only kept.

- The keyboard records by itself, so iOS's machinery for opening the app to record isn't here: no Keep Mic On (it keeps iOS's app recording in the background between dictations) and no held microphone. The mic switch at the top of Home, Transcripts, Clipboard and Stats (`micOn`, on unless you turn it off) says whether voice typing may use the microphone at all: off, the bar's mic opens iikb's Home instead of recording, and turning it off mid-dictation stops it and writes it down.
- The model is picked in Settings › Voice (`voiceModel`): Parakeet v3, the default, Parakeet Ultra, or Android's own recognizer in Apple's place. Android's never stands in for a Parakeet.
- The Parakeets are NVIDIA's parakeet-tdt-0.6b-v3 and Ultra, Moondream's post-training of it (`moondream/parakeet-ultra`, the same graph and tokens), int8, run on the CPU by sherpa-onnx (its Android library from GitHub's releases, `settings.gradle.kts`; one `libsherpa-onnx-jni.so` with ONNX Runtime linked in), each from sherpa-onnx's own export on Hugging Face. Each downloads on first use, about 670 MB at a pinned revision, each file checked against its SHA-256 and resumed where it stopped (`ModelFiles`), into the files Android doesn't back up. A dictation made while it downloads or loads is saved and written once it's ready; the bar shows its card and what it waits for. On the CPU the two take the same time, unlike iOS's Neural Engine, where Ultra's every load takes minutes; on his 578 dictations of 20 s or less (Nov 9, sherpa-onnx on the server) Ultra got 9.4% of words wrong to v3's 9.8%, and on the 212 of 4 s or less 7.6% to 10.7%.
- One loads as a dictation starts and is let go once nothing is left to write, since it holds the encoder's 650 MB; picking the other lets go of the first.
- A recording past the 15 s window is written in windows (`Windows`, FluidAudio's `ChunkProcessor` ported), so the encoder never holds more than 15 s: each ends at the latest pause in its last 5 s and the next starts there, or failing one, the next starts 2 s back at a quiet frame and the two are joined token by token. FluidAudio keeps pause cuts for encoders that run shorter windows for less, which sherpa-onnx's does on the CPU. A two-minute dictation on the 4 GB emulator (Nov 9) peaked at 0.98 GB written this way, against 2.2 GB in one pass, with Android killing other apps for memory, and was typed in 15 s against 20; on his 24 longest dictations (1 to 2½ minutes, on the server) it got 14.5% of words wrong to one pass's 14.7%, in half the time. FluidAudio's seam-gap repair isn't here: it accepts a re-heard gap only on Parakeet's word confidence, which sherpa-onnx doesn't give.
- Each is held to the Latin alphabet, as iOS's FluidAudio is with `language: .english`, since v3 leaves for Cyrillic on short or unclear English ("Сенты тусти." for "Send it to Steve." said with a Russian accent). sherpa-onnx has no such setting, so `LatinJoiner` writes the downloaded joiner again beside it (`joiner.latin.onnx`) with its last bias at -1e9 for each of the 1,720 tokens holding a letter outside it, so none can win. FluidAudio swaps such a token for the best Latin one; here a blank can win instead, so a word it can't hear as Latin may be left out rather than spelled. On those 578 dictations it changed nothing.
- `Microphones` picks the input, as iOS's `MicrophoneChoices`: Automatic is the phone's own or a wired or USB headset, never Bluetooth; a Bluetooth one is used only once picked in Settings › Voice, and only while connected, its device put on a call (`setCommunicationDevice`) only while you dictate. A device coming or going moves the recording onto the right input without a restart.
- Silero's voice-activity model downloads with it: a recording in which it hears no one is written as nothing, where Parakeet would write "Yeah." (sherpa-onnx gives no word confidence, which iOS also checks). Such a dictation is kept in Transcripts with its sound, as on iOS, and the bar says "Parakeet v3 heard nothing: it’s in Transcripts" (iOS's longer line doesn't fit beside the mic); a recording of a second or more with no sample past 100 of 32767 says the microphone gave no sound instead.
- Android's recognizer listens itself rather than writing a finished recording, so its dictations keep no sound.
- `Transcripts` keeps every dictation as a JSON line in `files/transcripts.jsonl` (`Transcript`: id, date in seconds since 1970, the text typed, seconds, whether it was typed, the model, the app's package, what the model heard when the style changed it, and whether it was recovered), and Parakeet's sound beside it as `no_backup/recordings/<id>.wav`, up to 512 MB. A recording without a transcript, left by a keyboard that ended first, is written the next time it starts, and never typed. A transcript's page sends its sound on as AAC (`RecordingShare`), to the phone's texting app or the share sheet, and Transcribe Again writes it with the model picked now: a Parakeet through `VoiceModel.write`, which takes one recording at a time from the keyboard and the app alike, or Android's recognizer, which from Android 13 hears a recording piped in (`AndroidSpeech.write`).

## Build

The toolchain is the Swift on the server (`swift --version`) and its Swift SDK for Android of the same version (`swift sdk list`), JDK 25, and the Android SDK in `~/Android/Sdk` with NDK r30 (`ndkVersion` in `app/build.gradle.kts`), linked into the Swift SDK by its `setup-android-sdk.sh`.

```sh
scripts/android                 # the signed release APK, built on the server
scripts/android --emulator      # and installed on the Mac's Android emulator
scripts/android --emulator drive.sh   # then drive.sh run on the Mac, holding the emulator's lock with the install
scripts/android-shots           # every screen, light and dark, under the names iOS's scripts/parity gives them, with its made-up data, into the parity page beside iOS's (SECTIONS="menu app" narrows it; OUT moves it)
```

Gradle builds the Swift library first (`swiftLibrary`, arm64 only, 16 KB pages). The release key lives in `~/.local/share/iikb/android` (`release.properties` beside `release.jks`), never in git; a build without it is unsigned.

The server has no hardware virtualization, so the emulator runs on the Mac (`~/Library/Android/sdk`, AVD `iikb`), one at a time, closed when done. Agents share it: drive it only from a script given to `scripts/android --emulator`, or under `lockf -k /tmp/iikb-emulator.lock` on the Mac (without `-k`, lockf deletes the file as it ends, and two runs can each hold a lock on a different file), so no other build is installed mid-test.
