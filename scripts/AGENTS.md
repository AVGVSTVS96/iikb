## Simulators

- They run on GitHub's free Macs, never Bassim's: `scripts/ci '<command>'` pushes this checkout's tree, uncommitted changes included, as a signed commit on a branch of its own (`ci/…`, deleted after), runs the command there through `.github/workflows/sim.yml` (Xcode 27.1, 3 CPUs and 7 GB, the iPhone Duo on iOS 27.2), prints the run's link and the command's output, copies `shots/raw/` back and exits as the command did. Each run gets a Mac of its own, up to five at once. GitHub hands queued runs to Macs in no set order, so while two runs wait in its queue, the next `scripts/ci` waits on this box ("waiting here for GitHub's queue to shorten"), one at a time: main's check after a push, which starts without `scripts/ci`, then finds a short queue. Every `scripts/ci` here reads one listing of the runs, fetched at most every 30 s, which keeps them inside GitHub's 5,000 calls an hour. `scripts/sim` refuses to run anywhere else, and `.github/actions/mac` sets up a run, for `shots.yml` too.
- Each boots slim with [simslim](https://github.com/mobai-app/simslim), without the ~170 iOS services no check uses (a third of the memory and CPU, measured in github.com/AVGVSTVS96/simlight); `SIM_WIDGETS=1` keeps the widget and App Intents services Control Center's controls need.
- `scripts/sim` creates its own `iikb …` simulators and enables the extension by writing `AppleKeyboards` (and, for iPad, `AppleKeyboardsExpanded = 1`) into the simulator's global preferences, so no Settings UI is needed.
- Simulators boot headless; the Simulator app never opens.
- Reference screenshots of Apple's keyboard come from the same simulators with `KEYBOARDS=system`.
- Builds are ad-hoc signed for the simulator (`CODE_SIGN_IDENTITY = -`), which embeds simulated entitlements, so the App Group works in the simulator without a team. Device builds need a team with the group `group.com.shahidy.iikb` registered.

## scripts/phone

It builds the app and keyboard with [xtool](https://github.com/xtool-org/xtool) from the root `Package.swift` and `xtool.yml` (their Info.plists are `Config/xtool/`, kept in step with `project.yml` by hand), and:
- signs them with the team's development profile that xtool renews on every run. It covers every device the team has registered (the iPhone and the iPad), so one build serves both; a new device gets registered by one direct `xtool install` to it.
- stamps main's commit count as the build number (Settings › About shows it), and builds only when something iikb is built from changed since the build on the link.
- builds nothing that fails `scripts/gate` (the bar), then `scripts/formats` (dictation's versions, decimals, percentages and addresses, and its cleanup) or `scripts/clean` (Clean's language model), each run on the commit it builds; the second reuses the first's build, so it adds seconds.
- puts the build on the install link: a page in your tailnet, opened in Safari on the iPhone or iPad from any network, where a tap on Install installs it over the air from a manifest (`itms-services`), keeping iikb's data. The link holds main's latest build, with its last changes under the button, and keeps the one before it for `scripts/rollback`. The page needs a trusted HTTPS address, which `tailscale serve` gives the folder it's in, set up once: `sudo tailscale serve --bg --set-path=/iikb-link ~/.local/share/iikb/link` on this Linux box (the Mac's App Store Tailscale can't serve a folder). `Config/link`, never committed, sets `url=` to that address.
- tells `Config/notify`, an executable never committed and given one line, why main can't get onto the link when a check, the build or signing fails or the Mac doesn't answer: once per reason, however many runs hit it, and once more when a build goes up again.
- puts the build in hangar too, when `~/Developer/hangar` is on this box: hangar is the iPhone app that installs every development app of Bassim's, with the build's new changes as its note. On a phone with hangar's Automatic installs on, hangar installs it by itself from the Mac in seconds; otherwise it waits for a tap on Update. `hangar put` prints which, and with Automatic installs on, scripts/phone waits for hangar's line saying the install ended before going on. Each build registers the URL scheme `com.shahidy.iikb-<build>`, which hangar opens after a tapped Update to know that build is installed and to bring iikb back up.
- prints the build on each device the Mac reaches by cable or Wi-Fi, which is how an agent knows whether its change is on the phone yet.

No install has a backup first (the app and keyboard send their files to the backup server as they change, docs/backup.md), and after one from the link or an automatic one nothing starts the app, so Parakeet compiles for a new build at its first dictation.

It needs:
- Swift 6.4.
- xtool built from [AVGVSTVS96/xtool](https://github.com/AVGVSTVS96/xtool). It signs with the real bundle and group IDs, so it updates the installed app and keeps its data, where stock xtool installs a separate `XTL-…` copy; and it keeps the App Group on free teams, which stock xtool drops, so iOS deletes the group's container.
- xtool's Darwin SDK: `xtool sdk install --slim` on an Xcode whose iPhoneOS platform also holds Xcode-beta's `iPhoneOS27.1.sdk`. The fork picks the newest iPhoneOS SDK for `arm64-apple-ios` and puts `-Xclang-linker -isysroot -Xclang-linker <its path>` in the bundle's `toolset-swb.json`. Never rebuild xtool while others build, since a rebuild that changes its Anisette provider logs it out.
- `xtool auth login`.

Linker facts:
- The keyboard target links with `-ObjC` because its principal class is only named in Info.plist.
- The Controls target links with `-u _main`: nothing references its widget bundle's `main`, so the linker otherwise leaves the whole control out of its static library, and xtool's signer then fails on the near-empty binary ("Can't find free space of LoadCommands").
- On Linux the Swift driver hands clang `--sysroot`, and clang reads an SDK's version only from `-isysroot`, so without that option the binaries record the deployment target (26.0) as their SDK. iOS 27.1 then runs iikb on the iPhone Duo as an old iPhone app, small and without the vertical bar, which the simulator never showed. `scripts/phone` refuses a build linked below 27.1, and the simulator runs use Xcode 27.1 so they show what the phone does.

## scripts/voiceloop

Dictation from the sound to what the keyboard types, scored against what it should have typed, so a fix to any part of it is chosen and checked by numbers:
- Its sets, in `voicebench/` beside the backup, never the repo (`scripts/voicecorpus.py` builds his):
  - real: Bassim's dictations against what each finally became, with the kind of field and the text before it from the transcript's `field`, or for one from before iikb kept them, from the record source's log. Four in five finals are what the iPhone typed, left as he got it, so there the reference is the build of its day: real's words wrong is mostly the bench straying from that build, and the iPhone's is his edit rate, neither an error rate. Its `edit: edited` line, the finals he changed, is the part a final can vouch for.
  - labelled: the dictations he's labelled by ear with `scripts/voicelabel` (100 picked by a hash of each id from every Parakeet v3 dictation, those with no final found included), against what he said: the one words-wrong that's an error rate, for the bench and the iPhone alike. Empty until he labels; the labels are kept in `~/.local/share/iikb/heldout/labels.jsonl`.
  - loud: quiet ones heard the commonest way (the front cardioid) mixed into his loud rooms heard that way, each room's stretches brought to the middle room's level before they're joined (`voicecorpus.room`), as said and up to 18 dB quieter, against his label or else the final: labelled ones first, the rest by a hash of each id from every quiet dictation (until Nov 15 only from those the iPhone had typed as he kept them, so its clean row was 0.4% wrong where any quiet dictation makes it 2.8%). A room is loud within 19 dB of how loud he usually sounds heard the same way (`voicecorpus.rooms`), since the cardioid hears his voice and his rooms 18 dB under iOS's own pick, which a single -40 dBFS mark was set for. A new loud dictation changes the room's sound, so all of them go through Parakeet again.
  - read: his dictations, since it was written, of `~/.local/share/iikb/heldout/read.txt`, 40 lines of emails, numbers, versions, links, times and money written blind on Nov 15 by an agent that never read iikb's code or formats.txt, each against what it should type. Empty until he reads it: each line dictated with iikb, one dictation per line, in any field.
  - spoken: `scripts/voicespoken.txt`'s made-up sentences (emails, phone numbers, codes, model versions, links, times, money, names), each with what iikb must type, said by three of six macOS voices in a quiet room, in his loud room and 18 dB softer there, and by Whisper in both (its `{name}` lines said with stand-ins and with names from his Dictionary, filled in outside the repo). It was written the afternoon the number and address code was, half its lines near copies of formats.txt's, so it's format coverage, not accuracy: read's the check on new text.
  - taps, below.
- Parakeet v3 writes each clip on the Mac as the app runs it (`Tools/VoiceBench`, in a turn), once per clip and version of that path: `voicebench/cache/` keeps what it wrote by the clip's sound and a hash of Tools/VoiceBench's code, links followed, so only new clips or a changed Parakeet path reach the Mac, and `--cached` leaves new clips out.
- Clean's model then answers each text Parakeet wrote, and the iPhone's Parakeet output where a set replays it, here as the app runs it (`VoiceEdit`, scripts/stages.py), once per text: `voicebench/cache/edits-<hash>.jsonl` keeps each reply as it comes, the hash of VoiceEditor's Swift (`Weights.shipped` included), VoiceEdit's and llama.cpp's release, so only new texts or changed weights or editing code run the model, and a first run cut short goes on where it stopped. A text takes about 0.65 s on this box, so a first run of about 4,000 takes some 45 minutes.
- The rest of the iPhone's path runs here (`Tools/VoiceBench/Text`, on a package of KeyboardCore alone): the app's writing style and Dictionary, which type the model's reply only where the settings replayed for that clip pick Clean and it's an edit of what was said, then the keyboard's `.dictated` in a field of that kind after the text before it and with the keyboard's saved memory (the words you type, which fix ones Parakeet mishears). His dictations get the settings, Dictionary and memory the iPhone had when each was said, the backup's newest copy written before it (the memory's from before that hour), never today's: today's memory learned from what he typed after, his fixes of these dictations included, his Dictionary gained terms for names these dictations misheard, and today's Texting style turned old Casual dictations' "you" into "u" (Nov 15: real 6.79% wrong with today's, 2.05% with each one's own, the text stage typing what the iPhone did on 742 and then 1,377 of 1,530). Those said before the backup's first copy (Nov 4) get that copy. The spoken set runs with the defaults and today's.
- Each set prints words wrong (um and uh, case and punctuation aside), dictations to fix (any word wrong) and dictations typed exactly, by group: length (under 5 s, 5 to 15 s, over 15 s, where Parakeet goes from one window to several), room, mic and kind of final for real; level for loud; condition, voice, topic, field and name for spoken. Short dictations hold few words (Nov 8: under 5 s, 23% of his dictations and 4% of the words, 6.65% of those wrong), so a change to them barely moves the whole set's words wrong: read their own line and the dictations to fix. Real also scores what the iPhone typed (`phone`) and the bench's text stage on the iPhone's own Parakeet output (`replay`), and counts how often each matches the iPhone's. Last, each set's count of dictations the bench typed the model's reply for.
- taps: every dictation the iPhone finished and typed nothing for, and how many of them the bench types words for (filler such as "Yeah.").
- Each set then lists the dictations the bench types differently since voiceloop's last run (`voicebench/last/`), worse, better or neither, by length, the worst shown, so a change that breaks a few dictations can't hide in the averages.
- Against his finals, which keep whatever the build of their day typed and lack what he cut after, four or more words in a row a final lacks that the iPhone typed too, alone or beyond the words they stand in for ("cut later"; words only the bench wrote are its own errors), and the same number in another form ("number form") are set aside, and punctuation and capitals count only against finals the keyboard followed (build 479 on). His references are scored as he left them, never put through the Dictionary, so a wrong Dictionary entry shows.
- Every remaining error is labelled by what the reference had there (emails, links, versions, times, money, digits, names, else words misheard, dropped or added) and ranked in `voicebench/categories.txt` with examples, and each dictation's texts go to `voicebench/<set>/loop.jsonl`.

## scripts/clean

The simple check on Clean's language model: what it must go on typing whatever weights ship, with the fruit list said without numbers first.
- Each `heard | typed` line of `scripts/clean.txt` goes through `VoiceEdit`, the app's own Packages/Voice/Sources/VoiceEditor with `Weights.shipped` (downloaded once into `~/.local/share/iikb/weights/<sha256>.gguf` and checked), then `VoiceText`, KeyboardCore at the defaults with Clean, as the start of a message types it (scripts/stages.py). A line passes when iikb types `typed` and it typed the model's reply, not the transcript without one.
- Since the lines run on that kept file, it also asks `Weights.shipped`'s URL for its headers (one request, redirects followed, 10 s at most) and fails, naming the URL, unless it answers with the file's size: weights an iPhone couldn't download never pass.
- Here it runs against llama.cpp built for this box at the release the app links (`scripts/llama`, once per release); x86 without Accelerate, so a reply that's a near tie can come out differently on the iPhone (VoiceEditor/AGENTS.md).
- Few lines on purpose: one is there because losing it is a regression anyone would notice. Scoring the model is scripts/rivals' job.

## scripts/eval

It types the MacKenzie & Soukoreff phrase set (500 phrases, 2,714 words) through `TypingEngine` with taps drawn from a Gaussian around the real key centers (`KeyGrid`, iPhone 17 width), seeded, and prints word accuracy without and with autocorrect and the top-3 suggestion hit rate, for three keyboards: (a) nearest key + `UITextChecker`, (b) iikb's decoder with the touch model held at its prior, (c) the decoder learning.

Its runs:
- `noise` reruns the original noise levels.
- `biasedThumbs` types the corpus twice as a user whose m, b and o land off target and prints a learning curve.
- `aimShift` types it once that way, then again after the user's aim moves (lower and right, o and e swinging the other way), and prints how fast the learning keyboard follows.
- `missedSpaces` types two, three and four words in a row from each phrase with every space's tap landing on the row above the space bar, and two and three with the spaces never typed, and prints how often the key map reads a tap as the space anyway, and how often the bar offers the words when it reads none.
- `strayKeys` types a word pair from each phrase in an Instagram field, on the iPhone's keyboard (@ and # beside the space bar) and on the open Duo's split one (between its space bars), with Auto-Correction off as iikb starts, and a memory of `chat.txt` rather than the phrases typed: the space's tap lands on @ or # from a thumb aimed at a plain field's space bar, and it prints how often the space after the pair reads it apart; and, with that tap aimed at the @ key instead, how often the pair stays as typed.
- `realTaps`, `realTypos` and `realAutocorrect` score real people's typing, which `scripts/realtyping.py` downloads into `build/real` (all CC BY 4.0; its header says what each holds): Google's and Vertanen & Kristensson's recorded taps replayed on iikb's grid; Aalto's sentences typed on phones with no autocorrect, typed again here letter by letter (word error rate before and after, typos fixed or in the bar, correct words broken); and the same dataset's iPhone and Android autocorrections, the word typed here after its own text (how often iikb and the phone each end on the word meant). Each person is in dev, to tune against, or test, the number to report.
- `predictions` scores the suggestion bar before each word (is the next word in the top 3, is it first) on the phrase set and on `chat.txt` (1,000 sentences from Taskmaster-1 user turns), for a new user and one whose memory keeps every phrase.
- `swipe` (not part of a full run, since it needs the 570 MB of swipe.futo.org's test and validation splits from `scripts/swipe data`) decodes the 48,355 test swipes whose word is letters and apostrophes through `Swipe.decode` and prints top-1/3/10 from the encoder alone and with the decoder, against iikb's lexicon and against it with every target added at a fixed frequency (the report adds them too; how common they're made moves top 1 by 2 points, so each of three is printed). It's diffed against eval.expected's `EVAL swipe` lines alone, which `swipeLanguages` and `swipeContext` print too.
- `swipeLanguages` (in a `swipe` run, once `scripts/swipe languages` has downloaded swipe-5) reads the swipes FUTO collected in German, French and Spanish, and in English on QWERTZ and AZERTY, each on the keys of the keyboard it was swiped on (its `layouts/` file) with the long-press letters of iikb's layout of it, against the language's downloaded words: from a–z's keys alone with the decoder, as swipe read before it read every key, then from every key by the encoder alone, and with the decoder where the keys are a–z's.
- `swipeTune` fits `Swipe.Scoring` on the validation split, or with `SWIPE_TUNE=languages` on every other swipe-5 swipe in another language, then scores the rest.
- `languages` (not part of a full run, since it downloads the published word lists the manifest names into `build/languages/`) types each other language's 500 phrases (`phrases.<id>.txt`, Common Voice's CC0 sentences) on its own layout with its own words and no next-word network, each language in its own process (about 25 minutes, all six at once). A letter no key shows is tapped on the key it's under, and an apostrophe a layout has no key for goes untyped. It's diffed against eval.expected's `EVAL language` lines alone.

It runs a Release build (the decoder is slow in Debug), here on Linux in a package of KeyboardCore, the word lists and `Evaluation` alone, which gives the same numbers as the Mac; only the baseline needs `UITextChecker`, so its lines are scored on a Mac (`scripts/ci scripts/eval`). A full run is diffed against `scripts/eval.expected` (the root AGENTS.md's rule table says what a change that moves the numbers owes).

## screens

The check that notices a screen nobody meant to change (`.github/workflows/screens.yml`):
- Four Macs shoot scripts/parity's screens side by side (`PARTS`: the keyboard light, dark, the app, Chats; three when only the keyboard changed, the app's pages carried over from the last run) with the clock stopped at `IIKB_NOW`: shots/demo's dates count back from it, `scripts/clock.c` stops the wall clock at it in iikb's app and keyboard only (through `DYLD_INSERT_LIBRARIES`, set in the simulator by `scripts/sim boot`), and the status bar reads 9:41. shots/demo/make.py writes the same data on every run, its files dated at `IIKB_NOW` too, and Swift's hashing is seeded the same in every launch, so ties keep their order. So two runs of one commit match pixel for pixel, but for GIF tiles (KLIPY's pictures, and they play), dictation's bar mid-recording, the swipe shot mid-trail, and the caret, with the Liquid Glass around each, which picks up their colors. The app's pages are shot without an outline, so there a mark the size of a caret or a spinner is left out.
- `scripts/screens.py` compares each shot with the last run on main's, leaving those out by where each shot's outline (`<screen>.json`, every element's identifier, label and frame from `ParityShots`) puts them, and names what moved, resized or reads differently where a screen changed. The run's summary has the report; its `report` artifact has before | after | change pictures.
- `scripts/screens-watch`, which `scripts/hooks/pre-push` starts here on a push to main, has a reviewer (Sonnet) look at each changed screen beside the commits since the run before, and sends Config/notify only what no commit says it changes.
- `scripts/duoshots` does the same on the real iPhone Duo, for what the simulator can't show: the `iikb-duoshots` user service (dotfiles) follows hangar's log, and when hangar opens a build on the phone after a tap on Update, the phone is awake with what Bassim just installed, so the Mac launches iikb with its keyboard up (`-iikbFocus`), light and dark, and shoots the lit screen with `devicectl device capture screenshot`. The launch doesn't always win the screen (iOS can keep the app Bassim is using in front), so `scripts/duoshot-check.swift` reads each shot with Vision on the Mac and only one of iikb's Home with iikb's keyboard up is kept; otherwise Config/notify hears what the shot showed instead. Each shot is compared with the last build's in the same pose (folded or open, tall or wide), the reviewer weighs it against the commits between the two builds, ignoring the status bar, the bar's words and the caret, which change on a real phone, and Config/notify hears the rest. Shots stay in ~/.local/share/iikb/duo/<build>/. A build installed from the install link, or by hangar's Automatic installs, which open nothing, isn't shot, so while Automatic installs is on no build is.
