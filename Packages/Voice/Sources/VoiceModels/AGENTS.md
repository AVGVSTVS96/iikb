# VoiceModels

The models that write a finished recording down (`VoiceModel`, `Parakeet`, `AppleSpeech`) and `VoiceProbe`, which times them on the iPhone. On VoiceCapture (for `Recording`), KeyboardStore and FluidAudio. What a model writes is styled in the app (App/Voice/AGENTS.md).

## The model

`VoiceModel.write` writes with the model you pick in Settings: Parakeet v3 (the default) or Parakeet Ultra through FluidAudio, on the Neural Engine, downloaded once from Hugging Face, or Apple's SpeechTranscriber.
- Apple's never stands in for a Parakeet. A dictation made while the picked Parakeet gets ready (its Neural Engine compile, after each install of a new build and each iOS update, takes 30 s to over 2 minutes) is recorded as any other and written once it's ready; the next one can be recorded meanwhile, and they're typed in the order said.
- Transcribe Again and a recording an ended app left, written as soon as the app starts, go through the same `write`.
- v3 is loaded when the microphone turns on and let go once it's off with nothing left to write, since it loads again in 0.1 s. Ultra, whose every load takes minutes, is kept. The simulator, which has no Neural Engine, loads one only when its microphone turns on, on the Mac's CPU.
- Each transcript keeps the model that wrote it, and once another writing is put in its place (Transcribe Again's Use This Transcript), what it was first written as.
- Builds before Nov 3 had Apple's model write a dictation made while a Parakeet got ready; each launch, `Transcripts.rewriteApple` writes those that kept their sound again with the picked Parakeet, one at a time while nothing is being recorded or written.
- A Parakeet reads the recording leveled (`Recording.leveled`: FluidAudio's Parakeets drop whole stretches of quiet speech) and held to the Latin alphabet (v3 otherwise drifts into Cyrillic).
- What it wrote is then styled in the Writing Style picked for the app it was said for (`Take.app`, from `Dictation.host`; Transcribe Again uses the transcript's app), read per field, capitalized and run through the Vocabulary in KeyboardCore (KeyboardCore/AGENTS.md, "Dictation's text").
- `scripts/voicebench` scores a change to that path, or a way to change it (`Tools/VoiceBench`: Dictionary boosting, LocalVQE, other models), on Bassim's own dictations against what each finally became, and on a loud set made from them, by room, mic and how each was heard: `uv run --with numpy scripts/voicecorpus.py` builds both from the backup into `voicebench/` beside it, never the repo, then `scripts/voicebench <corpus> dictation vocab …` runs each way on the Mac and `python3 -I scripts/voicescore.py <corpus> --misses <way>` prints what a way still gets wrong. Nov 5, on 590 dictations: v3 as the app runs it 1.58% wrong; CTC boosting of the Dictionary 1.72% (5.83% at FluidAudio's defaults), LocalVQE first 4.33%, Phonon-2 4.73%, Bark 3 4.87%, each worse in loud rooms too.
- Apple's on-device model (FoundationModels) doesn't choose a dictation's written forms, measured Nov 6 with `scripts/judgeprobe` on the Duo (iOS 27, AFM 3 Core Advanced, 8,192 tokens): asked to pick between a span's two written forms (guided generation, greedy, only the choices allowed, so it can't write a word not said), a warm call takes 220 to 280 ms, the first after launch 1.0 to 1.3 s, one after 30 s idle 1.8 s, and `prewarm` a second ahead saved nothing (440 ms). It chose worse than the rules: 26 of 40 made-up number and address twins ("the one two three button", "the code is one two three four five") to the rules' 40, and 5 of 11 context twins ("send it to Renner at fastmail.com", "the code is for eight to nine"), as the rules, keeping the words each time; on the Mac's macOS 26 model, 30 of 40 and 5 of 11. And a dictation is written while iikb is in the background, where it answered about 15 requests and then refused each as rate limited, and one cold request took 7 minutes. Such a span is in 3.7% of Bassim's dictations.
- `scripts/voiceloop` scores the whole path, from the sound to what the keyboard types, on those dictations and on a spoken set, and ranks what's still wrong by kind (scripts/AGENTS.md).

Measured on the iPhone Duo (iOS 27.2):
- v3's encoder compiles for the Neural Engine in about 17 to 37 s after each install of a new build and loads in 0.1 s after. That compile has iikb write about 500 MB (Core ML writes out the encoder's 425 MB of weights to compile them), against iOS's 1 GB a day before it files a disk-writes report: 4.3 GB in 97 minutes of installs on Nov 4. So `scripts/phone` installs only when something iikb is built from has changed. `VoiceModel.written` logs what iikb has written since it started with each load and dictation.
- Core ML keys what it compiles by the OS build, by the literal path a model loads from, and, for the parts loaded for the Neural Engine (encoder, decoder, joint), by the install. The app's own container moves to a new path with every install, so the Parakeets live in the App Group's container (`Library/Application Support/FluidAudio`, which the backup skips; `AsrModelVersion.folder` moved them over by rename), whose path installs keep, but the other three compile again after every install (Nov 5, builds 448 to 458).
- Core ML keeps what it compiles in the app's own caches, `Library/Caches/com.shahidy.iikb/com.apple.e5rt.e5bundlecache/<OS build>/<one folder per part and install>`, never the App Group's, and never removes an older install's: each install of v3 left about 36 MB on the Duo (and the encoder's 446 MB when it fell back to the CPU), 1.3 GB by Nov 5, and 1.1 GB in a simulator, 15 GB in one. So the first time an install, or an iOS update, reaches for a Parakeet's files, before any is loaded, `AsrModelVersion.folder` empties that cache; it costs only the preprocessor's 1 MB compile, the one part an install kept.
- Ultra's int8 encoder never caches there and takes 3 to 6 minutes, hot, every load (`scripts/voiceprobe`; FluidAudio #1022).
- Parakeet Unified, the English Parakeet Anomaly's iikb uses, gets 15% fewer of Bassim's words wrong than v3 (2.06% to 2.41% with um and uh set aside) but isn't offered: in FluidAudio 0.18.0 on the Duo it never runs on the Neural Engine, taking 77 s (int8) or 51 s (fp16) to load after a first compile of 5 to 8 minutes, and 9 to 16 s to write 37 s of talking, where v3 takes 0.05 s.
