# VoiceEditor

Clean's language model run on the iPhone's CPU: `Weights`, the file and how it's asked, and `Editor`, llama.cpp loading it and answering one transcript at a time. On llama.cpp alone (the `llama` binary target in Packages/Voice/Package.swift, llama.cpp's own xcframework from the release named there) and Foundation, nothing of iOS, so the bench and the gate build these very files on the Mac and on Linux (`scripts/stages.py`). `CleanModel` in VoiceModels is the app's whole view of it.

- What `Editor.edit` gives back is the model's reply as written. It never reaches a field but through KeyboardCore's `DictationWriting.written(_:edited:)`, which types it only as an edit of what was said (KeyboardCore/AGENTS.md).
- Swapping the model is a change to `Weights.shipped` alone: its name, size, URL (a release asset on iikb's repo, so the file behind it never changes) and SHA-256, and the frame it's asked in. `scripts/clean` then holds the new weights to scripts/clean.txt.
- The frame is written out in `Weights`, not rendered from the file's chat template, since llama.cpp's C API renders only templates it knows by name and has no switch for Qwen3's thinking. Its special tokens are read as tokens and the transcript's never, so nothing said can close the turn it sits in. Its start is decoded once per load and kept in the context between edits.
- CPU only: no devices and no GPU layers, since iOS refuses the GPU to an app in the background, where dictations are written, and iOS 27 limits the Neural Engine there too. The weights are mapped from the file and read in place, never repacked into memory of iikb's own, so they cost the app's memory nothing iOS counts. On Linux, at b10400 with the 397 MB own-1000: 373 MB mapped, a 224 MB context of 2,048 tokens, and 75 MB of working memory at 128 tokens a step (300 at llama.cpp's 512).
- Greedy, so the same transcript gets the same reply here, in the bench and on the iPhone up to float rounding: Nov 15, on the 372 bench transcripts, `VoiceEdit` on Linux gave the prototype's reply (llama-server b12428, which repacks the weights) for 359. Each of the other 13 was a near tie at its first different token, its two likeliest tokens 0.20 apart in probability at most (0.59 and 0.39), and 10 of them matched once the weights were repacked as llama-server does.
- A reply that reaches twice its transcript and 16 tokens more is thrown away (`ranOn`), as is a transcript that leaves no room for that in the context (`tooLong`); none of the 372 came near, the longest reply 1.05 times its transcript in characters.
- `Editor.draft` is the seam for the speed step: tokens the reply likely goes on with, checked in one batch with the token before them. It returns none yet. A guess is kept only where it's the likeliest token anyway, so drafting can't change a reply.
- `scripts/llama` builds the release Package.swift names for Linux, once, for the gate.
