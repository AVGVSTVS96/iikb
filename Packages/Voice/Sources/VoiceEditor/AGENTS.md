# VoiceEditor

Clean's language model run on the iPhone's CPU: `Weights`, the file and how it's asked, and `Editor`, llama.cpp loading it and answering one transcript at a time. On llama.cpp alone (the `llama` binary target in Packages/Voice/Package.swift, llama.cpp's own xcframework from the release named there) and Foundation, nothing of iOS, so the bench and the gate build these very files on the Mac and on Linux (`scripts/stages.py`). `CleanModel` in VoiceModels is the app's whole view of it.

- What `Editor.edit` gives back is the model's reply as written. It never reaches a field but through KeyboardCore's `DictationWriting.written(_:edited:)`, which types it only as an edit of what was said (KeyboardCore/AGENTS.md).
- Swapping the model is a change to `Weights.shipped` alone: its name, size, URL (a release asset on iikb's repo, so the file behind it never changes) and SHA-256, the longest transcript it edits, what it holds in memory, and the frame it's asked in. `scripts/clean` then holds the new weights to scripts/clean.txt, and fails until the URL serves a file of that size.
- The frame is written out in `Weights`, not rendered from the file's chat template, since llama.cpp's C API renders only templates it knows by name and has no switch for Qwen3's thinking. Its special tokens are read as tokens and the transcript's never, so nothing said can close the turn it sits in. Its start is decoded once per load and kept in the context between edits.
- A reply is text from the vocabulary's ordinary tokens alone. llama.cpp writes out an added token as text even with special tokens left out, and Qwen3's six added ones are markup (`<think>`, `</think>`, `<tool_call>` and the like): the development weights answer "Okay." with `</think>` alone. A reply with no text left is no reply (`empty`), and Clean types the dictation by its rules.
- CPU only: no devices and no GPU layers, since iOS refuses the GPU to an app in the background, where dictations are written, and iOS 27 limits the Neural Engine there too. The weights are mapped from the file and read in place, never repacked into memory of iikb's own, so they cost the app's memory nothing iOS counts. On Linux, at b10400 with the 397 MB weights, from llama.cpp's log: 372.65 MiB mapped; a 112 MiB KV cache for its context of 1,024 tokens (972 asked, which llama.cpp rounds up), 224 MiB at 2,048; 77.44 MiB of working memory at 128 tokens a step (300.75 at llama.cpp's 512); and 0.58 MiB of output. `Weights.memory` is those last three, 190 MiB.
- Greedy, so the same transcript gets the same reply here, in the bench and on the iPhone up to float rounding: Nov 15, on the 372 bench transcripts, `VoiceEdit` on Linux gave the prototype's reply (llama-server b12428, which repacks the weights) for 359. Each of the other 13 was a near tie at its first different token, its two likeliest tokens 0.20 apart in probability at most (0.59 and 0.39), and 10 of them matched once the weights were repacked as llama-server does. All 372 replies came out the same again at the context of 1,024 with the limits below.
- The weights say the longest transcript they edit (`Weights.longest`, 400 tokens, about 300 words: none they were trained on is longer), and the context holds the frame, that and its reply alone. A longer transcript gets no reply before anything is decoded (`tooLong`), and Clean types it by its rules. A reply may run to twice its transcript and 16 tokens more, never more than 160 past it; one that reaches that is thrown away (`ranOn`). Of the 372 the longest reply was 1.05 times its transcript in characters. What reaches it is a sentence said over and over: said 20 times (360 tokens), it ran to 520 tokens in 37 s on a loaded Linux box, Nov 15.
- `Editor.draft` is the seam for the speed step: tokens the reply likely goes on with, checked in one batch with the token before them. It returns none yet. A guess is kept only where it's the likeliest token anyway, so drafting can't change a reply.
- `scripts/llama` builds the release Package.swift names for Linux, once, for the gate.
